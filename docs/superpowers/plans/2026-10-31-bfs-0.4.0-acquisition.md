# BFS 0.4.0 Acquisition Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Do not commit, push, or delegate unless explicitly authorized.

**Goal:** Add HTTP-page ZIP discovery and policy-controlled downloads into staging, followed by the existing BFS ingest pipeline, for version 0.4.0.

**Architecture:** Three independently usable commands share one TOML file: `discover` writes a candidate inventory, `download` selects and transfers candidates into managed staging, and `ingest` consumes only verified completed transfers. Existing local-path ingestion, ZIP safeguards, repositories, and exports retain their current behavior.

**Tech Stack:** Existing Rust, clap, serde/TOML, tempfile, SHA-256, and cancellation primitives. Add one blocking HTTP client with TLS and one HTML parser; verify current official documentation, Rust compatibility, licensing, and dependency footprint before choosing versions. Prefer a blocking design; do not introduce an async runtime or browser automation.

**Spec:** The agreed workflow and proposed implementation decisions are recorded below. This is a reviewable plan, not authorization to implement it. Unanswered product details receive explicit defaults below.

## Global Constraints

- Target BFS version `0.4.0`; no product code changes during planning.
- Preserve existing flat runtime TOML configuration and CLI override precedence.
- Support HTTP and HTTPS pages with direct ZIP links; no recursive page crawling.
- Download and extraction budgets are independent.
- Keep download directories private (0700) and downloaded payloads sealed (0000), reusing `security::private_dir`, `security::seal`, and `security::validate_file`; never execute downloaded content or overwrite unrelated files.
- Do not reset, discard, commit, or push changes without authorization.
- Never persist credentials, authorization headers, or secret URL query parameters in output or errors.
- Preserve existing sealed-storage and archive-derived filename restrictions.

## Review Focus

- Links with relative paths, HTML entities, fragments, repeated URLs, and misleading suffixes produce a stable, bounded inventory (Task 2).
- Missing or false Content-Length and concurrent transfers cannot bypass byte budgets (Task 3).
- Redirects to another origin cannot silently broaden the configured source scope (Tasks 2 and 3).
- Interrupted writes and changed staged files cannot be mistaken for complete downloads (Tasks 3 and 4).
- Repeated runs from different staging roots retain source identity without breaking old manifests (Task 4).

## Proposed 0.4.0 contract

These defaults are implementation proposals, especially the title and date semantics, rather than claims of prior user approval.

### Commands and configuration

```sh
bfs discover --config collection.toml
bfs download --config collection.toml --dry-run
bfs download --config collection.toml
bfs ingest --config collection.toml --dry-run
bfs ingest --config collection.toml
```

`discover` performs bounded page requests and writes metadata; it never fetches resource bodies. `download --dry-run` is offline: it reads the saved inventory and reports ordered candidates and known sizes without claiming an exact final sorted layout. Existing ingest preview still reads, hashes, and classifies downloaded payloads.

Keep existing ingest fields at the TOML root. Add optional acquisition tables; do not invent a nested `[ingest]` schema that breaks existing config loading.

```toml
input_mode = "archives"
output = "./sorted.zip"
zip = true
rules = "./rules.example.toml"

[source]
page = "https://example.org/downloads/"
same_origin = true
max_page_size = "5 MB"

[download]
inventory = "./collection/inventory.jsonl"
staging_dir = "./collection/downloads"
max_files = 100
max_file_size = "1 GB"
max_total_size = "10 GB"
max_staging_size = "20 GB"
concurrency = 3
timeout_seconds = 300
# Optional site limits, shared across workers:
max_speed = "2 MB/s"
min_request_interval_ms = 1000
max_requests = 100
order_by = "title"
order = "ascending"
directory = "{title}"

[[download.policies]]
title_contains = "Linux"
action = "include"

[[download.policies]]
title_contains = "Deprecated"
action = "exclude"
```

- Resolve relative paths against the process working directory, matching existing BFS behavior; document this clearly.
- Accept integer quantities with `B`, `KB`, `MB`, `GB`, `TB`, `KiB`, `MiB`, `GiB`, `TiB`; decimal units use powers of 1000, binary units powers of 1024. Reject negative, fractional, unitless strings, overflow, and zero limits. Existing integer ingest limits remain unchanged.
- Default acquisition limits are the values above. Existing extraction defaults remain unchanged: a file accepted for downloading may still exceed configured extraction limits; document this explicitly.
- Each download invocation attempts at most `max_files` non-cached candidates. `max_total_size` bounds resource-body bytes read during that invocation, including failed downloads. `max_staging_size` bounds managed completed and in-progress payload bytes, including leftovers from interrupted runs; it is not a guarantee about whole-filesystem free space.
- Optional `max_speed` accepts a positive integer byte quantity followed by `/s`, using the same decimal/binary units as size limits (for example `"500 KB/s"` or `"2 MiB/s"`). It caps aggregate resource-body read throughput across all download workers, not each worker separately; omitted means unlimited. Use a shared monotonic-clock byte pacer with at most one bounded read-chunk burst, not a separate rate-limiting dependency. This limits application reads, not exact TCP traffic buffered by the OS.
- Optional `min_request_interval_ms` spaces the starts of HTTP requests across workers; zero or omitted disables spacing. Optional positive `max_requests` caps actual requests per command invocation; omitted means unlimited. Both apply to discovery and download requests, including redirect hops. Budgets reset between separate commands/processes; no persistent or cross-process site scheduler.
- Count and pace each actual request before sending it, including redirects; use explicit bounded redirect handling so HTTP-client automatic redirects cannot bypass the limiter. Cache hits and offline previews consume no requests. No implicit HEAD probes or automatic retries. If the request cap prevents selected work, report incomplete execution and return nonzero.
- HTTP 429 stops new requests to that origin for the invocation, reports `Retry-After` when valid, and returns an incomplete result; do not retry automatically or sleep indefinitely. Already active requests may finish within existing budgets. Waits for spacing/speed must respond promptly to cancellation and count toward the configured transfer timeout.
- One metadata control directory contains inventory, completion receipts, and a staging lock. Payloads live in a separate managed subtree; ingest never recursively scans control files.
- Acquisition config must not silently replace explicit ingest inputs: explicit CLI paths or configured root `inputs` win. Only when neither exists does ingest use the completed-download inventory.

### Discovery, titles, dates, and policies

- Parse HTML anchors and resolve URLs against the final page URL, honoring the first valid HTTP(S) HTML base URL subject to origin rules. Strip fragments, preserve query semantics, and deduplicate normalized URLs.
- Select links whose URL path ends in `.zip`, case-insensitively. Download endpoints without that suffix are out of scope for 0.4.0.
- `same_origin = true` requires the page origin for resource links and redirects, including page redirects; reject origin changes. With `false`, allow HTTP(S) redirects only, with a maximum of five hops. Never downgrade HTTPS to HTTP.
- Title means normalized visible anchor text; fall back to the decoded URL basename if empty. Keep the first nonempty title for duplicate links. Do not infer a surrounding heading or execute JavaScript.
- `name` means decoded URL basename, not an untrusted Content-Disposition path. Store the original separately from sanitized local names.
- For 0.4.0, `date` means discovery timestamp in UTC, not publication date. Store one timestamp per discovery run. Explain this in CLI help; do not guess publication dates from HTML or HTTP Last-Modified.
- `order_by` accepts `title`, `name`, or `date`; compare normalized lowercase text for title/name and UTC timestamps for date. Use source identity as deterministic tie-breaker; support ascending/descending.
- Policies support exactly one of `title_contains` or `name_contains`, plus include/exclude action. Matching uses normalized lowercase text. Exclusions win; if include policies exist, at least one must match. No scripting, regex DSL, or date-range policies in this release.
- `directory` accepts `{title}` or `{name}`, or a literal safe relative directory. Sanitize components, bound lengths, refuse traversal and platform-reserved names, and append a stable source-ID suffix to prevent collisions. Original ZIP names remain recognizablSource	Feasibility

### Transfer and persistence

- Model a candidate as stable source ID, resource URL, title, name, and discovery timestamp. Compute source ID from normalized resource URL; do not include staging paths or discovery time.
- Query strings may contain signed credentials. 0.4.0 rejects URL userinfo and resource/page URLs containing query strings rather than persist secrets or invent a credential store. Report this limitation without echoing the full rejected URL.
- Save a versioned inventory atomically in private storage; reject malformed, oversized, or unsupported inventory records. An explicit successful rediscovery replaces the candidate snapshot; failures preserve the previous inventory. Download receipts remain independent of that snapshot.
- Receipts contain source identity, stable source metadata, safe relative payload path, size, and SHA-256. Write one atomic receipt per completed resource only after payload sync/publication. Never derive trust solely from filename or file presence.
- One downloader owns a staging root at a time. Validate existing managed staging paths and refuse symlinks and unexpected files. Count orphan partial payloads against staging limits; report them without deleting automatically.
- Use private temporary files, bounded streaming reads, finite timeouts, shared cancellation, and an atomic shared byte budget. Disable transparent response decompression and request identity encoding so resource bytes and accounting agree. Size headers are advisory; enforce observed bytes.
- When a file limit is exceeded, fail that file and remove its owned partial on normal exit. When run/staging budgets are exhausted, stop new work and cancel active transfers; never publish partial files. Charge each body read to the shared budget before issuing the read by reserving a bounded chunk and releasing unused reservation. A simple synchronized budget is sufficient.
- No automatic retry or byte-range resume in 0.4.0. A rerun validates receipt ownership, size and sealed permissions before skipping a sealed completed file; it must not unlock the file to rehash it. Missing files or unexpected permissions cause an actionable error. Full hash verification happens after explicit user unlocking, before ingestion.
- Continue independent per-file failures, report each candidate as downloaded/cached/filtered/failed/not-attempted, and return existing-style codes: 0 complete success, 2 mixed success/failure, 1 failure without success or interruption. Intentional filtering is not failure; budget-blocked selected candidates mean incomplete execution and nonzero exit.
- Stage retention is explicit: keep completed downloads after ingestion. No automatic cleanup or destructive cache eviction.
- Seal payloads to 0000 immediately after opening their creation handles, as existing extraction does; write/hash through that handle, close it before publication, and verify sealed permissions. Control metadata stays 0600 and directories 0700 (directory traversal permission is required; do not chmod directories to 0000). Fail closed if permissions cannot be enforced.
- Separate download and ingest commands cannot reopen 0000 files. Preserve the existing prohibition on automatic unsealing: the user explicitly unlocks selected receipt-owned payloads to 0600 before ingest/preview; the documented example must show this manual permission step. Ingest verifies Standard permissions and receipt hash, then uses existing repository sealing. No new unlock command, permission framework, or automatic permission changes.
- Document the boundary accurately: sealed permissions prevent ordinary reopening/execution; they are not a noexec mount or sandbox and cannot prevent the owner/root from changing permissions or running an interpreter on an explicitly unlocked file.

### Ingest integration and identity

- Both input modes remain explicit: archives opens ZIP contents; files keeps downloaded ZIPs as ordinary files. No automatic archive recursion or mixed-mode inference.
- Preserve downloaded origin/title/name/date as optional provenance in occurrence metadata. Stable remote occurrence IDs derive from source ID + entry index + extracted content hash, not temporary local paths. Existing local occurrence IDs remain unchanged.
- Add backward-compatible optional provenance fields; old manifests continue loading and archive safety restrictions still apply. New provenance must not change existing rule placeholders or imply title-based sorting of extracted entries in this release.
- Staging placement and download priority are separate from existing extracted-content rules. Title is used for acquisition policy and staged directory naming; sorting extracted contents continues using existing rules.
- Ingest resolves exact receipt-owned payloads, validates them against their receipts, and fails before publishing outputs if any selected completed payload was modified. Unfinished downloads are excluded and reported. Existing ZIP output still requires a fully successful ingest run.

## Acceptance criteria

- A user can preview discovered ZIP URLs/titles, preview policy selection offline, download within enforced budgets, and ingest verified staged files using one TOML file.
- Discovery and download reruns do not overwrite unrelated files, lose prior successful downloads, or duplicate remote source identities merely because staging paths changed.
- Network failures, malformed inventories, modified cache files, cancellation and extraction failures are visible and cannot produce apparently successful incomplete ZIP exports.
- Existing local ingest/config/tests remain compatible; new functionality ships as BFS 0.4.0.

## Deferred scope

Hugging Face adapters, authentication/signed URLs, SFTP/FTP and upload servers, recursive crawling, browser automation, surrounding-heading selectors, publication-date parsing, date-range policies, nested archive recursion, non-ZIP extraction, retries/range resume, automatic cleanup, direct network-to-extractor streaming, a combined `run` command, and title-based rules for extracted contents.
